# Native lot host

A real Rust `GameRuntime` authority loaded from a sealed cooked release. Its only transport is a private line-delimited supervisor pipe. It must not be attached directly to a browser or unauthenticated network endpoint: commands include trusted spawning and memory writes.

Start with `wonderland-native-lot-host CONFIG.json`. The strict schema-1 config requires release_dir, independently obtained binding_sha256, lot_file, lot_sha256, mode (`Tso`/`Ts1`), and canonical decimal-string lot_id, authority_epoch, lot_incarnation, seed, utc_start_dotnet_ticks, effect_namespace. The release directory contains binding.json, manifest.json and verified digest-named `.wlp` packs. The pinned lot file uses bounded fixed-integer bincode encoding of `LotModel`, not a default fixture. Paths and files must remain immutable for this process lifetime. Observed symlinks and traversal are refused; this is not a hostile-filesystem sandbox.

Ordinary initial and `inspect` messages contain the committed checkpoint/cursor, sealed release report and effective runtime content descriptor. A takeover starts with an explicitly tentative `recovery_candidate` until exact-marker activation, as described below. These two content identities are distinct because GameRuntime attaches interaction tables.

`prepare` accepts one bounded vector of ticks containing server-admitted commands, encoded as fixed-integer bincode hexadecimal. It requires exact binding and predecessor. A separate candidate runtime executes those commands. The returned `proposal` is for coordinator validation/storage only; its ticks and effects are not permission to publish or dispatch. Unknown acceptance retains the candidate and prevents a successor. A matching `committed` digest and cursor installs it; rejection discards it. `lookup` and same-input retry return the existing pending/terminal result. Consumers deduplicate terminal results by batch ID/digest; repeated retrieval is not a new delivery.

Frames retain the existing WLR1 binary encoding. Durable build requests/results/faults and routing callbacks have a tick/ordinal-tagged binary supervisor-events lane. They remain speculative until commit. Effect dispatches use bincode hex so their 64-bit operation identities never lose precision in a JavaScript JSON parser. JSON lot/epoch/incarnation/tick/batch identities are canonical decimal strings.

Bounds: 1 MiB input lines, 256 KiB command bytes, 16 ticks × 128 commands per proposal, 8 MiB checkpoints, 16 MiB encoded proposal payload, 4,096 in-memory receipt entries and 32 MiB total retained terminal receipt bytes. Capacity exhaustion fails closed; receipts are not silently evicted.

## Checkpoint-anchored receipt custody

The private `export_receipts` command exports an exact, sorted prefix of at most 64 terminal entries and 16 MiB. Each entry retains the original request hash, proposal digest and entire terminal reply, including correlated action receipt bytes and rejected decisions. The envelope binds the host identity, current committed cursor and checkpoint digest. Export and new acknowledgement both refuse unresolved pending candidates and unactivated recovery.

After publishing and read-back verifying that checkpoint, the coordinator's private `persistHostReceiptsV1` verifies terminal decisions against its retained ledger, stores the exact envelope in content-addressed R2 storage, verifies readback and atomically indexes every record. Only its digest-bound `persisted` acknowledgement may be passed to `acknowledge_receipts`. An exact repeat acknowledgement is idempotent. Changed binding, cursor, checkpoint, prefix watermark or receipt-set digest fails without deleting receipts. An oversized individual receipt that cannot fit one export fails closed and stays in memory.

Acknowledgement retires only that exported prefix and advances a permanent in-process batch-ID watermark. Every prepare/resolve/lookup at or below it returns `retired`, never re-executes, even for an unused ID within the retired range. The supervisor must call private `lookupHostReceiptV1` with incarnation and batch ID, compare the original input hash for prepares or digest for resolves, then return the exact historical terminal reply. A missing record or mismatch is a hard failure. Terminal retrieval never republishes effects or runs the candidate again. The browser runner implements this custody transfer after its 32-tick checkpoints and earlier when retained receipts reach 8 MiB; it drains additional bounded pages before resuming.

The host trusts its private pipe for durable assertions, as it already does for commit decisions. A state checkpoint is not a receipt database. The browser runner always recovers into a new incarnation, so restarted batch numbering cannot reuse an old binding. Other supervisors doing same-incarnation restarts must retain their durable batch allocation/retry ledger; no receipt watermark is inferred from a simulation checkpoint.

This custody transfer preserves records actually archived before retirement. It does not reconstruct a missing action correlation if the host dies in the pre-existing window between durable batch commit and host resolve/export: accepted state and effects remain in the coordinator journal, but the original action request is not part of that proposal. The player's unresolved result remains `Unknown` through recovery and is never inferred successful or automatically replayed. Closing that separate window requires persisting original request/correlation metadata before commit.

## Actual process verification

Build the existing `runtime-bridge` executable, then `cargo build -p wonderland-native-lot-host --all-targets` and `node tools/hosted-game/verify-host-boundary.mjs`. The test release is explicitly authored, passes through the production cooker, and has its source inputs removed. The new service itself contains no fixture fallback. The test checks real behavior mutation and matching accepted-wire replay, speculative isolation, pending/commit/reject/retry/lookup, changed input, malformed identities and bounded inputs.

## Pinned restart recovery

An optional `recovery` object supplies checkpoint_file, checkpoint_sha256 and expected_cursor. Optional tail_file/tail_sha256 must be supplied as a pair; additional_tail_files contains file/sha256 pairs. Up to 64 total tail files share an aggregate 8 MiB and 64-frame bound. The checkpoint has its own 8 MiB bound. All files are independently hash-pinned. Exact-current checkpoints need no tail files. The existing runtime snapshot restore verifies its content/lot/epoch binding. The tail must be a WLR1 accepted-tick packet with at most 64 frames; every resulting state hash and the final committed cursor must match. Startup emits no ready state on any mismatch. Without takeover, this restores the same epoch only. An optional `takeover` field carries the private coordinator's recorded RecoveryGrantV1. After proving the old committed cursor and snapshot digest, the loader validates exact successor epoch/incarnation and invokes the narrow GameRuntime epoch-adoption method. The process emits `recovery_candidate` and refuses prepare until the supervisor has completed the durable anchor and sends `activate_recovery` with the exact TakeoverMarkerV1. An altered marker is refused; exact repeat activation is idempotent. No speculative replacement state is labeled committed.

## Release limitations

The private companion `services/native-edge` now provides a locally qualified durable journal and verified checkpoint storage. Authenticated account grants, deployed ownership orchestration, browser publication gateway, automatic wall-clock tick scheduling and EOD/economic providers remain unfinished. The process accepts supervisor decisions because the pipe is the trust boundary; it does not prove an external database committed. Before deployment Task 3 must persist proposals/results and fence incarnations, and Task 4 must authenticate player admission. The process journey also exercises nonempty dialog effects and durable build requests with identities beyond JavaScript’s safe integer range. Full original-content coverage and actual original-BHAV process qualification remain separate acceptance gates. Never substitute this local service test for hosted gameplay completion.
